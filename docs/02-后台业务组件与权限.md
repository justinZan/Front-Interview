# 02｜后台业务、组件封装与权限

这一章对应岗位中的“复杂页面与表单表格”“前端路由与权限管理（菜单级、按钮级）”“与后端联调”。建议边读边实现一个**设备管理页**。

## 学完应该能做什么

1. 设计设备列表、详情、编辑、告警确认等页面的数据流。
2. 根据权限控制菜单、路由和按钮，并能解释前后端各自负责什么。
3. 处理筛选、分页、排序、请求竞态、加载、空数据和异常状态。
4. 封装业务组件时给出清楚的输入、输出和扩展点。
5. 与后端约定接口字段、错误码、时间和实时数据协议。

## 1. 先画清业务模型与数据流

能源监控后台常见实体：

| 实体 | 例子 | 前端常见操作 |
|---|---|---|
| 站点 | 光伏站、储能站、充电站 | 筛选、总览、拓扑入口 |
| 设备 | 逆变器、电池簇、采集器 | 列表、详情、在线状态、编辑 |
| 测点 | 功率、电压、温度、SOC | 实时值、历史曲线、单位和精度 |
| 告警 | 过压、通信中断 | 推送、确认、恢复、查询历史 |
| 用户与角色 | 运维、管理员、访客 | 可见菜单、操作权限、数据范围 |

先把“接口数据”“页面状态”“用户操作”分开。例如设备页面的数据流：

```text
筛选表单 → 查询参数 → 设备分页接口 → 列表状态 → 表格渲染
                     ↘ 错误/空状态    ↗
点击设备 → 详情接口 → 详情抽屉
点击编辑 → 表单校验 → 提交接口 → 成功后刷新当前页
实时推送 → 根据设备 ID 更新在线状态；历史列表仍以查询接口为准
```

### 推荐的目录职责

```text
src/
  api/devices.ts          # 请求和 DTO 类型
  stores/auth.ts          # 跨页面的身份与权限
  router/index.ts         # 路由及访问控制
  pages/devices/          # 页面编排
  components/             # 稳定可复用的业务组件
  composables/            # 可复用的交互/状态逻辑
```

**设计原则**：页面组件负责组合；API 模块隔离网络细节；store 存放跨页面共享状态；只在确实复用时抽取组件或 composable。设备列表的筛选条件通常由页面持有，登录用户与权限适合放到 store。

## 2. 路由、菜单、按钮权限

### 2.1 先定义统一的权限标识

```ts
// 这些标识由前后端约定；真实项目通常来自后端权限配置。
type Permission =
  | 'device:read'
  | 'device:create'
  | 'device:update'
  | 'alarm:ack'

type CurrentUser = {
  id: string
  name: string
  permissions: Permission[]
}

function hasPermission(user: CurrentUser, required: Permission) {
  return user.permissions.includes(required)
}
```

**要想清楚**：权限、角色、数据范围不是一回事。角色可以汇总权限；数据范围决定“能看哪些站点/设备”，不能只靠前端过滤接口返回的数据。

### 2.2 路由保护

路由元信息可以附加访问要求，导航守卫在进入页面前判断。下面是精简示意，`restoreSession()` 代表从可信会话接口恢复用户信息；实际项目还要处理请求失败和重定向后的返回路径验证。

```ts
import { createRouter, createWebHistory } from 'vue-router'
import { useAuthStore } from '@/stores/auth'

const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/login', name: 'login', component: () => import('@/pages/Login.vue'), meta: { public: true } },
    { path: '/403', name: 'forbidden', component: () => import('@/pages/Forbidden.vue') },
    {
      path: '/devices',
      name: 'devices',
      component: () => import('@/pages/devices/DeviceList.vue'),
      meta: { permission: 'device:read' },
    },
  ],
})

router.beforeEach(async (to) => {
  if (to.meta.public) return true

  const auth = useAuthStore()
  if (!auth.initialized) await auth.restoreSession()
  if (!auth.user) return { name: 'login', query: { redirect: to.fullPath } }

  const required = to.meta.permission as Permission | undefined
  if (required && !auth.user.permissions.includes(required)) {
    return { name: 'forbidden' }
  }
  return true
})
```

若采用动态路由，登录后按权限注册路由，退出时移除已注册路由。`router.addRoute()` 只会**注册**路由；如果当前 URL 已经在该地址，还需要重新导航或在守卫中返回目标地址。具体行为见 [Vue Router 动态路由文档](https://router.vuejs.org/guide/advanced/dynamic-routing)。

### 2.3 菜单与按钮

菜单最好从一份声明式配置生成，再按权限过滤，减少“菜单有入口但路由不能进”的不一致。

```ts
const menuItems = [
  { label: '设备管理', path: '/devices', permission: 'device:read' },
  { label: '告警中心', path: '/alarms', permission: 'alarm:ack' },
] as const

const visibleMenus = menuItems.filter(item =>
  currentUser.permissions.includes(item.permission),
)
```

按钮级控制可以先用明确的条件渲染：

```vue
<el-button
  v-if="auth.user?.permissions.includes('device:update')"
  @click="openEdit(row)"
>
  编辑设备
</el-button>
```

当大量页面重复同一种规则时，再封装 `PermissionButton` 或指令。封装后仍须能传递 `loading`、`disabled`、插槽、点击事件等原始能力。

**安全边界**：前端隐藏按钮和阻止路由，是界面体验；用户可以直接发 HTTP 请求。服务端必须对每个接口检查身份、权限及设备/站点的数据范围。面试时把这一点主动说清楚。

### 2.4 高频追问

**问：刷新页面后动态路由消失怎么办？** 先恢复登录状态与权限，再注册需要的路由，最后进入目标页。注意“权限加载中”不能被当成“无权限”；否则刷新时会错误跳转到 403。

**问：角色变更或退出登录怎么办？** 使权限缓存失效，清除用户相关状态，移除动态路由，重新计算菜单；同时后端会话失效。多个标签页还需考虑状态同步。

**问：菜单级与按钮级权限的差异？** 菜单级决定入口和可访问页面，按钮级决定页面内操作。都应使用统一的权限标识；后端分别对读取与变更接口授权。

## 3. 复杂表格：一个可解释的数据请求模型

### 3.1 明确请求与响应类型

```ts
type DeviceStatus = 'online' | 'offline' | 'fault'

interface DeviceQuery {
  keyword: string
  status?: DeviceStatus
  siteId?: string
  page: number
  pageSize: number
  sortBy?: 'name' | 'updatedAt'
  sortOrder?: 'asc' | 'desc'
}

interface DeviceRow {
  id: string
  name: string
  siteName: string
  status: DeviceStatus
  updatedAt: string // 接口约定 UTC ISO 8601；显示时再本地化
}

interface PageResult<T> {
  items: T[]
  total: number
  page: number
  pageSize: number
}
```

接口返回的数据类型（DTO）有时和界面展示模型不同。例如功率由 W 转为 kW、状态码转为文案，应在明确的一层转换，避免每个表格单元格重复转换。

### 3.2 请求竞态与取消

用户快速输入关键词或连续切换筛选条件时，先发出的旧请求可能后返回，覆盖新数据。`AbortController` 可以取消旧请求；即使网络库不能真正取消，也可以用递增请求序号忽略过期响应。

```ts
import { ref, watch, onUnmounted } from 'vue'

const query = ref<DeviceQuery>({ keyword: '', page: 1, pageSize: 20 })
const rows = ref<DeviceRow[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref<string | null>(null)
let activeController: AbortController | undefined

async function loadDevices() {
  activeController?.abort()
  const controller = new AbortController()
  activeController = controller
  loading.value = true
  error.value = null

  try {
    const result = await fetchDevicePage(query.value, controller.signal)
    if (controller.signal.aborted) return
    rows.value = result.items
    total.value = result.total
  } catch (e) {
    if (controller.signal.aborted) return
    error.value = '设备列表加载失败，请重试'
  } finally {
    if (activeController === controller) loading.value = false
  }
}

watch(query, loadDevices, { deep: true, immediate: true })
onUnmounted(() => activeController?.abort())

function applyFilters(filters: Pick<DeviceQuery, 'keyword' | 'status' | 'siteId'>) {
  query.value = { ...query.value, ...filters, page: 1 }
}
```

`fetchDevicePage` 是 API 层函数，需传递 `signal` 给 `fetch` 或所用请求库。输入框可在提交时查询，或采用防抖；不要让每个按键都无条件请求。改变筛选/排序时通常重置到第 1 页，改变分页大小时还要判断当前页是否越界。

### 3.3 完整的页面状态

| 状态 | 界面表现 | 用户下一步 |
|---|---|---|
| 首次加载 | 骨架或加载提示 | 等待；避免出现“假空表” |
| 无结果 | 清楚区分“暂无设备”和“当前筛选无结果” | 新建设备或清空筛选 |
| 请求失败 | 错误提示与重试 | 点击重试，保留筛选条件 |
| 提交中 | 禁止重复提交，显示进度 | 等待结果 |
| 部分实时失联 | 保留已加载数据，标识数据可能过期 | 手动刷新或等待重连 |

## 4. 表单与组件二次封装

### 表单开发顺序

1. 和产品/后端明确字段、单位、必填条件、可编辑状态和提交后行为。
2. 用类型描述表单值；把校验规则与界面提示写清楚。
3. 提交时再做一次前端校验；服务端仍应校验。
4. 提交期间锁定按钮；成功后关闭弹窗或跳转，并刷新受影响数据。
5. 服务端返回字段级错误时定位到字段；未知错误保留表单输入并允许重试。

以“额定功率”为例：字段名、单位 W/kW、允许范围、小数位、空值含义、后端存储单位必须一致。很多联调问题来自单位或时区不一致，不是表单库本身。

### 组件封装判断

适合封装：多个页面共用、业务含义稳定、交互契约清楚的控件，例如站点选择器、设备状态徽标、带权限的操作区。

不宜过早封装：只在一页出现、字段或样式持续变化的巨大“万能表格”。过多配置项会让调用者难以理解，尤其在自定义列、可编辑单元格和权限操作同时存在时。

封装一个 `SiteSelect` 时，至少回答：

- 输入：`modelValue`、可选站点范围、禁用状态、占位文字。
- 输出：`update:modelValue`、加载失败或选择变化事件。
- 状态：加载、无站点、错误、只读。
- 扩展：是否允许搜索、远程过滤、单选/多选。
- 类型：站点 ID 用字符串还是数字？空值用 `null` 还是空字符串？

## 5. 接口联调清单

联调前用一份表格和后端对齐：

| 主题 | 必须确认的问题 |
|---|---|
| 分页 | 页码从 0 还是 1 开始？`total` 是否包含全部筛选结果？ |
| 筛选 | 空参数表示不限还是筛选空值？多选如何编码？ |
| 时间 | 是否统一 ISO 8601/UTC？秒还是毫秒？时区如何显示？ |
| 数值 | 功率/电量单位、精度、`null` 含义、负值含义 |
| 错误 | 状态码、业务错误码、字段错误结构、可重试条件 |
| 权限 | 无权限是 401 还是 403？数据范围由哪个接口保障？ |
| 实时 | 快照/增量格式、事件 ID、序号、心跳、断线补拉入口 |

对接口时保存**最小真实样例**：正常、空列表、部分字段缺失、无权限、网络失败、重复或乱序推送。基于这些样例做 mock，可以先完成界面和异常路径，再联调真实服务。

## 6. 面试题与示范回答

### Q1：如何实现菜单级和按钮级权限？

**回答结构**：服务端返回用户权限标识 → 前端用统一配置生成可见菜单，并用路由元信息保护页面 → 操作按钮按权限渲染 → 每个接口由服务端重新鉴权。补充刷新后的权限恢复、退出时清理、角色变化时缓存失效、数据范围授权。

**加分点**：说明“隐藏按钮”不等于安全；即使页面 403，攻击者仍可手动请求接口。

### Q2：复杂表格如何避免筛选和分页状态混乱？

**回答结构**：定义唯一的查询对象；筛选变化时页码归 1；查询对象驱动请求；显式处理加载/空/错误；取消或忽略旧请求；提交编辑后按场景刷新当前页。若用户需要分享查询结果，可把筛选条件同步到 URL。

### Q3：什么时候把状态放入 Pinia？

**回答结构**：多个不相邻页面要共享、或跨页面需要持续存在的状态适合 store，例如用户、权限、当前站点。单页表单开关和临时筛选优先保留在页面；可复用逻辑可以用 composable。把所有东西放全局会增加耦合与清理成本。

### Q4：怎样判断一个组件封装是否成功？

**回答结构**：调用侧能通过清楚的 props/events/slots 完成需求；组件内部只承担稳定职责；对加载/错误/空值有一致行为；支持必要的扩展而不过量配置。可用两个不同业务页面复用验证，若总要加特殊分支，应重新看边界。

### Q5：如何和后端处理“接口文档与实际返回不一致”？

**回答结构**：保留请求与响应样例，指出不一致字段及影响，与后端确认契约和兼容策略；在 API 适配层集中处理临时兼容并加注释/清理条件；回归正常与异常场景。不要在多个组件中散落兜底逻辑。

## 7. 动手练习与验收

### 练习 A：设备管理页

实现列表筛选、分页、排序、详情抽屉、编辑表单。用 mock 数据至少覆盖 2000 台设备、空结果、接口 500、慢响应。切换筛选条件时验证旧响应不会覆盖新响应。

**验收**：浏览器刷新可保留合理的路由状态；数据变化后页码与总数正确；失败有重试入口；提交中不会重复发送。

### 练习 B：角色切换

配置管理员、运维、只读三个角色：管理员能编辑设备，运维能确认告警，只读只能查看。页面菜单、路由和按钮都按权限变化。模拟直接调用无权限 API，说明为什么必须由服务端拒绝。

**验收**：刷新后权限可恢复；切换角色或退出后旧菜单和旧路由不可见；403 与 404 有不同提示。

### 练习 C：联调说明

为设备列表写一页接口契约，包含分页、过滤、状态码、单位、时间、错误体以及三个 JSON 样例。面试时用这页文档解释你如何降低联调成本。
