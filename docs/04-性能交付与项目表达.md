# 04｜性能、交付与项目表达

本章对应岗位要求中的首屏加载、懒加载、虚拟滚动、大数据表格、响应式布局与大屏适配，以及测试联调、构建部署、文档和跨团队协作。学习目标是能在面试中拿出**测量数据、定位过程、方案取舍和验证结果**。

## 阅读路线

1. 用浏览器工具建立性能基线，再学习首屏和运行时优化。
2. 做一个设备列表：先分页，再在确有需要时加虚拟滚动。
3. 做一个监控大屏：在不同分辨率下验证布局与图表尺寸。
4. 把接口联调、测试、构建部署串成一次完整交付。
5. 按本章模板准备项目讲解与行为题。

## 1. 性能问题先测量，再优化

### 1.1 需要分清的几类问题

| 现象 | 常见原因 | 先看什么 |
|---|---|---|
| 页面打开慢 | HTML/JS/图片大、接口慢、资源串行 | Network 瀑布图、构建产物、LCP |
| 点击后反应慢 | 主线程长任务、复杂计算、频繁重渲染 | Performance 录制、INP 相关交互 |
| 页面跳动 | 图片/图表无尺寸、异步内容插入 | CLS、元素尺寸变化 |
| 滚动卡顿 | DOM 行数过多、昂贵样式或同步布局 | DOM 节点数、Performance 中 Layout/Paint |
| 图表卡顿 | 点数和更新频率过高、反复初始化 | 更新耗时、数据量、实例生命周期 |
| 使用一段时间后变慢 | 监听器、定时器、图表/连接未释放 | 内存快照、组件卸载后资源数量 |

LCP 反映主要内容显示速度，INP 反映交互响应，CLS 反映布局稳定性。它们是用户体验指标，不等同于“接口返回时间”。具体阈值和工具说明以 [web.dev Core Web Vitals](https://web.dev/articles/vitals) 为准。

### 1.2 一次可复现的排查流程

1. **固定环境**：记录页面、数据量、浏览器、设备、网络、是否冷缓存、构建版本。
2. **记录基线**：至少采集加载耗时、关键请求耗时、JS 体积和交互录制；可重复 3 次，报告中位数。
3. **定位主因**：Network 看等待时间和传输量；Performance 看脚本、样式计算、布局、绘制；Vue Devtools 看组件更新。
4. **一次只改一类问题**：例如先拆分重型图表路由，再测量首屏变化。
5. **对比结果**：相同条件下记录优化前后数值，并检查功能、错误率和内存是否回退。

示例记录表：

| 场景与条件 | 指标 | 优化前 | 优化后 | 主要改动 |
|---|---:|---:|---:|---|
| 设备列表，1 万条模拟数据，冷启动 | 可交互时间 | 实测填写 | 实测填写 | 服务端分页/虚拟滚动 |
| 首页，弱网环境，冷缓存 | 入口 JS 传输量 | 实测填写 | 实测填写 | 路由级懒加载 |

不要把示例表中的空位编造成生产指标；面试时明确它们来自练习环境或真实项目。

### 1.3 面试题

**问：首屏加载慢，你会怎样优化？**

答题顺序：确认页面与网络条件 → 看关键资源和 LCP 元素 → 区分服务端等待、资源下载、JS 执行、渲染瓶颈 → 选择措施 → 再测量。措施包括压缩和缓存静态资源、路由懒加载、按需加载图表、控制首屏接口数量、给图片明确尺寸。骨架屏改善等待感受，但不能代替实际加载优化。

**追问：Lighthouse 分数很高，用户仍说慢？**

实验室环境与真实用户的设备、网络、缓存、数据规模不同。需要查看实际用户数据或从用户环境复现；也要确定用户抱怨的是首屏、筛选、滚动还是点击。用单一总分替代业务场景容易误判。

## 2. 首屏、懒加载与请求管理

### 2.1 路由级拆分

```ts
// src/router/routes.ts
import type { RouteRecordRaw } from 'vue-router'

export const routes: RouteRecordRaw[] = [
  {
    path: '/devices',
    name: 'devices',
    component: () => import('@/views/DeviceListView.vue'),
  },
  {
    path: '/dashboard',
    name: 'dashboard',
    component: () => import('@/views/DashboardView.vue'),
  },
]
```

这样图表页代码可在进入图表页时加载。拆分之后仍需看构建产物和网络瀑布图：过多小 chunk 可能增加请求和维护成本。大型依赖是否单独拆分，要根据实际页面访问模式和缓存收益判断。

### 2.2 旧请求覆盖新筛选结果

用户快速改筛选条件时，请求 A 先发、请求 B 后发，但 A 可能后返回。用 `AbortController` 取消旧请求，并仍检查当前请求身份，因为取消并不保证所有封装层都立即停止后续处理。

```ts
import { ref, onBeforeUnmount } from 'vue'

type Device = { id: string; name: string; online: boolean }
type PageResult = { items: Device[]; total: number }

export function useDeviceSearch() {
  const rows = ref<Device[]>([])
  const total = ref(0)
  const loading = ref(false)
  const error = ref<string | null>(null)
  let controller: AbortController | null = null
  let requestId = 0

  async function search(keyword: string, page: number) {
    controller?.abort()
    controller = new AbortController()
    const currentId = ++requestId
    loading.value = true
    error.value = null

    try {
      const params = new URLSearchParams({ keyword, page: String(page) })
      const response = await fetch(`/api/devices?${params}`, {
        signal: controller.signal,
      })
      if (!response.ok) throw new Error(`HTTP ${response.status}`)
      const data = (await response.json()) as PageResult
      if (currentId !== requestId) return
      rows.value = data.items
      total.value = data.total
    } catch (cause) {
      if (currentId !== requestId) return
      if (cause instanceof DOMException && cause.name === 'AbortError') return
      error.value = cause instanceof Error ? cause.message : '请求失败'
    } finally {
      if (currentId === requestId) loading.value = false
    }
  }

  onBeforeUnmount(() => controller?.abort())
  return { rows, total, loading, error, search }
}
```

实践中还要处理鉴权、统一错误码、分页边界和筛选改变时页码归 1。不要因为一次接口很快就忽略竞态；较慢网络或后端抖动才容易暴露问题。

### 2.3 练习

- 用浏览器网络节流模拟弱网，比较路由同步引入与懒加载的首页资源。
- 连续输入筛选词并快速翻页，观察是否出现“旧结果覆盖新结果”。
- 为设备列表建立加载、空数据、错误、重试四种状态。

## 3. 大数据表格与虚拟滚动

### 3.1 先选数据策略

**服务端分页**适合可以按条件查询的设备列表：前端只接收当前页，接口提供 `total`、排序和筛选。它能减少网络和浏览器内存压力，通常是第一步。

**虚拟滚动**适合用户确实需要连续滚动很多行的场景：保留完整数据模型，但只渲染视口附近的 DOM。它减少 DOM 数量，不减少已下载的数据量；若一次接收百万条记录，仍要分页或窗口化获取数据。

**窗口化数据获取**适合高规模、连续浏览：前端只保存附近页面数据，滚动到边界时追加/移除。它比普通分页复杂，要处理总数、滚动位置和缓存。

### 3.2 定高虚拟列表的核心计算

假设每行高度 `rowHeight = 48px`，容器高度 `viewportHeight = 480px`，滚动位置 `scrollTop = 960px`：

- 首个可见索引约为 `floor(960 / 48) = 20`。
- 可见行数约为 `ceil(480 / 48) = 10`。
- 再加前后缓冲行，例如各 5 行，以减少滚动边界的白屏。
- 总占位高度仍是 `totalRows * rowHeight`，渲染窗口通过 `transform: translateY(startIndex * rowHeight)` 放到对应位置。

最小示意代码：

```ts
const rowHeight = 48
const overscan = 5

function getWindow(scrollTop: number, viewportHeight: number, total: number) {
  const visibleStart = Math.floor(scrollTop / rowHeight)
  const visibleCount = Math.ceil(viewportHeight / rowHeight)
  const start = Math.max(0, visibleStart - overscan)
  const end = Math.min(total, visibleStart + visibleCount + overscan)
  return {
    start,
    end,
    offsetY: start * rowHeight,
    totalHeight: total * rowHeight,
  }
}
```

真实表格还要处理固定表头、固定列、横向滚动、行选择、键盘焦点和可变行高。可变行高不能继续用简单的 `index * rowHeight`，需要测量并维护偏移量。已有组件库若支持虚拟表格，应先评估其 API 和边界行为。

### 3.3 面试题

**问：10 万条设备数据要展示，为什么不能直接 `v-for`？**

答：大量 DOM 节点会增加创建、布局、绘制、内存和更新成本。先确认产品是否真的需要一次浏览全部数据；通常用服务端筛选/分页。若需要连续滚动，再加虚拟列表，并测量滚动流畅度、节点数和内存。

**追问：虚拟表格点击某行后向下滚动再回来，勾选状态丢失怎么办？**

答：虚拟化会复用或卸载行组件，选中状态应按稳定业务 ID 存在表格外的状态集合或后端，而非只放在行组件的局部状态；列表使用稳定 `key`。

### 3.4 练习

- 用 1 万条模拟数据展示普通表格与虚拟表格，记录 DOM 节点数和滚动表现。
- 添加排序、选中、固定列，检查虚拟化后的状态和对齐。
- 使用实际业务接口时比较“服务端分页”和“一次加载后虚拟滚动”的网络量。

## 4. 响应式布局与监控大屏

### 4.1 先确定布局目标

后台管理页通常希望在笔记本和桌面显示器上**重新排版**：侧边栏、筛选区和表格列随空间变化。监控大屏通常要求在固定比例的展厅屏上**保持整体视觉结构**，但要兼容不同分辨率和 16:9 以外的比例。选方案之前先列出目标设备尺寸、最小可用宽度、是否允许滚动、图表是否必须全屏可见。

```css
.dashboard {
  display: grid;
  grid-template-columns: minmax(18rem, 1fr) minmax(28rem, 2fr) minmax(18rem, 1fr);
  gap: clamp(12px, 1vw, 24px);
  min-height: 100vh;
  padding: clamp(12px, 1.5vw, 28px);
}

@media (max-width: 1100px) {
  .dashboard {
    grid-template-columns: 1fr 1fr;
  }
}

@media (max-width: 700px) {
  .dashboard {
    grid-template-columns: minmax(0, 1fr);
  }
}
```

对于必须保持设计稿比例的展示屏，可以在外层计算缩放比例，但要检查文字可读性、留白、鼠标命中范围和浏览器缩放。单纯用 `transform: scale()` 不会改变文档流占位，父容器和图表尺寸仍需单独处理。

### 4.2 图表尺寸随容器变化

```ts
import { onMounted, onBeforeUnmount, ref } from 'vue'
import * as echarts from 'echarts'

const chartEl = ref<HTMLDivElement | null>(null)
let chart: echarts.ECharts | null = null
let observer: ResizeObserver | null = null

onMounted(() => {
  if (!chartEl.value) return
  chart = echarts.init(chartEl.value)
  chart.setOption({ /* 业务配置 */ })
  observer = new ResizeObserver(() => chart?.resize())
  observer.observe(chartEl.value)
})

onBeforeUnmount(() => {
  observer?.disconnect()
  chart?.dispose()
  observer = null
  chart = null
})
```

若容器初始为隐藏状态或尺寸是 0，要在其真正显示且完成布局后初始化或调用 `resize()`。仅监听 `window.resize` 可能遗漏侧边栏展开、面板拖动等容器尺寸变化。

### 4.3 面试题

**问：大屏在 1920×1080 正常，换 4K 后图表变小或留白，如何处理？**

答：先确认设计基准比例和实际容器尺寸；区分分辨率变化、设备像素比和浏览器缩放。布局层用栅格、弹性尺寸或有边界的整体缩放；图表容器用 ResizeObserver 触发 resize；再在目标屏幕验证文字、交互和性能。不要只按屏幕宽度直接等比放大字号。

### 4.4 练习

- 在 1366×768、1920×1080、3840×2160，以及窄比例窗口中截图检查布局。
- 展开/收起侧栏后检查图表是否重新铺满容器。
- 测试图表隐藏后再显示的尺寸和清理逻辑。

## 5. 接口联调：从协议到异常场景

### 5.1 联调前确认的契约

| 类别 | 要确认的具体问题 |
|---|---|
| 地址与环境 | 各环境 base URL、代理、HTTPS、跨域策略 |
| 身份认证 | token/cookie 方案、续期、过期码、权限码 |
| 数据字段 | 字段名、类型、空值、单位、时间和时区、枚举含义 |
| 列表 | 页码从 0 还是 1 开始、排序字段、总数含义、最大 page size |
| 错误 | HTTP 状态与业务码分工、字段级校验错误格式 |
| 实时推送 | 订阅主题、心跳、序号、重连补偿、告警去重 |
| 兼容性 | 新旧字段过渡、接口版本、可选字段的默认值 |

示例接口约定应包含成功、空数据、权限不足、字段缺失、服务端错误和超时样例。前端拿到样例后可以先建类型和 mock，联调时再对照真实响应。

```ts
type DeviceStatus = 'online' | 'offline' | 'warning'

interface DeviceDto {
  id: string
  name: string
  status: DeviceStatus
  powerKw: number | null
  updatedAt: string // 约定为带时区的 ISO 8601 字符串
}

function formatPower(value: number | null): string {
  return value === null ? '暂无数据' : `${value.toFixed(1)} kW`
}
```

注意：TypeScript 的 `interface` 只在编译期检查，不能验证运行时从网络来的 JSON。对不受控数据或高风险字段，应在边界做运行时校验；避免未经验证的类型断言掩盖接口变化。

### 5.2 常见联调问题及处理

- **前端看到 200 但业务失败**：确认业务码及错误消息，统一拦截层是否吞掉错误。
- **时间差 8 小时**：确认服务端时间是否含时区、前端解析和展示时区；不要反复人工加减小时。
- **图表断点**：区分 `0`、`null` 和没有数据；明确补点/插值规则。
- **重复请求**：看组件挂载、watch、路由切换、请求重试是否同时触发。
- **接口字段改名**：建立契约版本和变更沟通，集中在 DTO 映射层处理。

### 5.3 面试题

**问：后端接口尚未完成，你怎样推进前端开发？**

答：先对齐契约和样例 payload，确认字段、状态和错误场景；用 mock 数据实现 UI 与状态流；把依赖项列出来并约定联调时间；真实接口出来后替换数据源，核对类型、异常和边界，不把 mock 当作真实行为的证明。

## 6. 测试与质量保障

### 6.1 测试层次

| 层次 | 适合测试 | 本岗位例子 |
|---|---|---|
| 单元测试 | 纯函数和状态转换 | 功率单位换算、告警去重、权限判断 |
| 组件测试 | 组件输入与可见输出 | 表单校验、空状态、按钮权限 |
| 端到端测试 | 关键用户路径 | 登录 → 设备筛选 → 查看详情 → 处理告警 |
| 手工探索 | 易变布局和复杂交互 | 4K 大屏、图表缩放、断线恢复 |

优先测易出错的业务规则和关键流程。为了达到覆盖率而重复测试框架本身，价值有限。

### 6.2 单元测试示例（Vitest）

```ts
// src/utils/alerts.ts
export type Alert = { id: string; version: number; message: string }

export function keepLatestAlerts(input: Alert[]): Alert[] {
  const latest = new Map<string, Alert>()
  for (const alert of input) {
    const current = latest.get(alert.id)
    if (!current || alert.version > current.version) latest.set(alert.id, alert)
  }
  return [...latest.values()]
}
```

```ts
// src/utils/alerts.test.ts
import { expect, it } from 'vitest'
import { keepLatestAlerts } from './alerts'

it('同一告警保留版本更高的一条', () => {
  expect(keepLatestAlerts([
    { id: 'A', version: 2, message: '恢复' },
    { id: 'A', version: 1, message: '触发' },
  ])).toEqual([{ id: 'A', version: 2, message: '恢复' }])
})
```

这是有意义的行为测试：消息乱序到达时仍保留较新版本。若系统没有 `version`，应与后端约定可比较的序号或时间戳，并明确它是否可靠。

### 6.3 端到端测试的思路

端到端测试应覆盖关键路径，而不是把每个 UI 细节都写成脆弱的定位器。例如使用稳定的 `data-testid` 定位设备搜索框，mock 接口返回确定数据，断言结果、加载态、错误态和权限入口。实时功能可用受控的模拟推送，复现断线、补拉和重复消息。对图表的测试可优先验证数据映射与可见交互，复杂视觉呈现再做截图/手工检查。

### 6.4 上线前检查

- [ ] 关键路由能直接刷新进入，权限不足和 404 行为正确。
- [ ] 列表的加载、空、错误、重试及分页边界已检查。
- [ ] 实时连接断开、恢复、页面离开和重复消息已检查。
- [ ] 图表在容器变化后正常，组件卸载后无多余连接和监听器。
- [ ] 生产构建成功；接口地址、静态资源路径和缓存策略符合部署环境。
- [ ] 相关角色的菜单、按钮和接口权限都通过联调验证。

## 7. 构建与部署

### 7.1 Vite 环境变量的边界

```ts
// Vite 项目示例
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL
```

`VITE_` 前缀变量会进入客户端代码，可被最终用户查看，因此只放公开的配置，如 API 地址或功能开关。密码、签名密钥、服务端 token 等应留在后端或部署平台的服务端配置。构建时的值与运行时的值要区分：如果希望同一份构建产物用于多环境，可由服务端提供运行时配置文件，具体方案需与部署团队约定。

### 7.2 SPA 部署常见问题

1. **刷新深层路由返回 404**：服务器需将未知页面路径回退到应用入口 HTML，同时保留 API 和静态资源路径的正常处理。
2. **新版本上线后页面白屏**：旧 HTML 引用了已删除的哈希资源；部署时应控制 HTML 缓存、保留一段时间的旧资源或安排原子发布。
3. **静态资源路径错误**：核对 Vite `base` 与部署子路径。
4. **线上 API 跨域/混合内容**：确认 HTTPS、代理和 CORS 配置，不依赖开发服务器代理解决生产问题。
5. **排障困难**：记录发布版本，按安全策略管理 source map 和前端错误日志。

### 7.3 一份最小交付文档应包含

- 项目用途、主要页面和技术栈。
- 本地启动、环境变量、mock 切换、构建命令。
- 目录结构和重要架构决策。
- API 与实时消息契约、错误处理和权限边界。
- 部署路径、回退方案、已知限制和验证记录。

### 7.4 面试题

**问：开发环境正常，生产环境刷新 `/dashboard` 后 404，如何定位？**

答：确认是浏览器直接请求该路径时服务器返回的 404，还是前端路由内部 404。若是前者，检查静态服务器的 SPA 回退规则，确保 API 与静态资源不被错误回退；再验证部署子路径和 Vite `base`。

**问：上线后旧用户偶发白屏，刷新后恢复，可能是什么？**

答：先看控制台和资源请求。若旧页面引用的哈希 chunk 在部署时被删除，动态 import 会失败；应调整 HTML/静态资源缓存和发布过程，必要时提供一次性安全刷新提示，并用发布版本定位。

## 8. 项目讲解：让面试官看到自己的贡献

### 8.1 2 分钟讲解模板

> **背景**：这是一个用于查看站点设备状态和告警的监控后台，主要用户是运维人员。  
> **目标**：页面需要在大量设备、实时推送和大屏展示下保持可用。  
> **职责**：我负责设备列表、实时状态与趋势图，参与接口契约和发布验收。  
> **关键决策**：列表先采用服务端分页；实时数据使用快照加增量事件，断线后重新拉取；图表按时间窗口限制点数。  
> **结果**：给出真实测量条件及前后数据，或说明练习项目的可复现观察。  
> **复盘**：最初遇到的竞态/尺寸问题怎样被定位和修复，下一步如何改进。

把模板替换成自己的真实项目。面试官通常会追问“为什么这么做”“还有什么方案”“效果怎样证明”“你具体写了哪部分”。讲述时区分团队成果和个人贡献。

### 8.2 技术难点故事模板

| 部分 | 需要准备的信息 |
|---|---|
| 具体问题 | 什么页面、什么数据规模、什么可见故障 |
| 定位证据 | 性能录制、网络请求、日志、用户反馈、复现步骤 |
| 备选方案 | 至少两个可选方案及其限制 |
| 自己的决策 | 为什么选择当前实现，谁参与确认 |
| 验证结果 | 数值、回归范围、上线观察；没有指标就说明事实边界 |
| 复盘 | 后续监控、文档或架构改进 |

示例：设备列表初版一次加载全部记录，滚动时 DOM 数量高、页面卡顿。先与产品确认是否需要跨页连续浏览；若不需要则改服务端分页。用同一数据规模对比渲染时间与节点数，并核对筛选、排序、选中状态。这个故事比泛泛地说“我做了虚拟滚动优化”更能说明判断力。

### 8.3 行为面试练习题

1. **需求频繁变化，接近上线你如何处理？**
   - 说明怎样确认验收条件、区分必须项和后续项、评估回归范围并同步风险。
2. **与后端对字段理解不一致怎么办？**
   - 给出具体字段、样例和业务影响；协商契约、记录结论、补充 mock 和回归场景。
3. **线上出现故障，你负责的模块可能有问题怎么办？**
   - 先止损和定位影响范围，再用日志/指标重现；与相关同事合作排障，发布修复并复盘。
4. **你没有物联网业务背景，如何快速理解能源流图？**
   - 先建立站点、设备、测点、功率/电量和告警的术语表，拿一个真实站点走完整数据流，再与业务方核对边界。

### 8.4 自测标准

- 能在 2 分钟内清楚讲完项目，且不混淆个人贡献与团队成果。
- 每个技术难点都能回答“为什么”“替代方案”“如何验证”。
- 对没有直接做过的技术能解释实验计划，不编造经验。
- 项目 README 能让面试官在 5 分钟内找到启动方式、演示页面和架构说明。
