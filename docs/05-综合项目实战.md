# 05｜综合项目实战：能源设备实时监控台

这份练习把岗位要求串成一个可讲解的项目。目标是让面试官看到你能完成**后台页面、实时数据、图表、权限、性能和交付**的完整闭环。可以先使用 mock 服务，之后再替换成真实后端。

## 1. 业务设定

假设你为运维团队开发一个多站点监控台。运维人员需要在一个页面看到站点功率、设备在线状态和最新告警；需要筛选设备、查看曲线、确认告警。管理员还可以编辑设备资料，只读用户只能浏览。

### 最小可交付范围

| 模块 | 必须实现 | 可以后补 |
|---|---|---|
| 登录与权限 | 三种模拟角色、菜单/路由/按钮控制 | 接入真实身份服务 |
| 设备管理 | 筛选、分页、详情、编辑 | 批量导入导出 |
| 监控概览 | 指标卡、功率曲线、在线设备统计 | 地图、复杂组态图 |
| 告警中心 | 告警列表、实时新增、确认状态 | 多级通知策略 |
| 实时连接 | 连接状态、重连、去重、补拉 | 多标签连接复用 |
| 质量交付 | README、错误状态、构建说明 | 自动化部署 |

先做可运行的最小范围，再增加复杂拓扑或能量流图。这样每一阶段都有能演示的成果。

## 2. 技术方案与目录建议

建议以 Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus（或 Ant Design Vue）+ ECharts 实现。技术栈与岗位一致。目录示例：

```text
src/
  api/                   # HTTP 请求与返回类型
  components/            # 设备状态、站点选择器等稳定组件
  composables/           # useDevicePage、useRealtime 等逻辑
  pages/
    dashboard/           # 指标和图表
    devices/             # 列表、详情、编辑
    alarms/              # 告警列表
  router/                # 路由配置与守卫
  stores/                # 用户/权限/当前站点
  types/                 # 共享业务类型
  utils/                 # 单位、时间、数值格式化
mock/                    # HTTP 与实时消息的模拟数据
docs/                    # 架构、接口契约、性能记录
```

工程边界：`api` 只负责与服务端通信；页面管理业务交互；composable 管理可复用状态逻辑；图表组件负责实例生命周期；业务数据和图表配置分离。

## 3. 数据契约示例

设计接口时先把时间、单位、空值语义写下来。下面是练习用的一个约定，实际项目需和后端确认。

```ts
type DeviceStatus = 'online' | 'offline' | 'fault'

interface Device {
  id: string
  siteId: string
  name: string
  status: DeviceStatus
  powerKw: number | null // null 表示无有效测量值，不等于 0
  updatedAt: string      // UTC ISO 8601，如 2026-11-15T12:00:00Z
}

interface Alarm {
  id: string
  deviceId: string
  level: 'info' | 'warning' | 'critical'
  state: 'active' | 'acknowledged' | 'recovered'
  occurredAt: string
  message: string
}
```

### HTTP 接口草案

| 请求 | 用途 | 核心参数/响应 |
|---|---|---|
| `GET /api/devices` | 查询设备 | `siteId/status/keyword/page/pageSize` → `items/total` |
| `GET /api/devices/:id` | 获取详情 | 设备静态资料 + 最新测点 |
| `PATCH /api/devices/:id` | 编辑资料 | 可编辑字段，不允许客户端覆盖实时测点 |
| `GET /api/dashboard?siteId=...` | 初始快照 | 指标、最近曲线、最新告警 |
| `GET /api/events?after=...` | 断线补拉 | 上次事件 ID 之后的事件 |
| `POST /api/alarms/:id/ack` | 确认告警 | 最新告警状态；服务端校验权限 |

### 实时事件草案

```json
{
  "eventId": "evt-1025",
  "sequence": 1025,
  "type": "device.measurement",
  "siteId": "site-a",
  "deviceId": "dev-7",
  "occurredAt": "2026-11-15T12:00:05Z",
  "payload": { "status": "online", "powerKw": 18.4 }
}
```

`eventId` 用于去重与补拉游标；`sequence` 可用于判断缺口或顺序；`occurredAt` 是事件发生时间，不等于浏览器收到时间。项目中可以先保证**同一站点内**序号递增，避免过早设计跨站点全局顺序。

## 4. 分阶段实现

### 阶段 1：静态页面和 HTTP 数据

1. 搭建主布局、登录页、404/403 页面。
2. 做设备列表：搜索、状态/站点筛选、分页、加载/空/错误状态。
3. 做设备详情和编辑表单，处理字段校验与提交失败。
4. 做告警列表和确认按钮，模拟角色权限。

**完成标准**：用 HTTP mock 跑通主要流程；刷新页面仍能正确进入允许的页面；快速切换筛选条件不会显示旧请求结果。

### 阶段 2：图表与大屏

1. 在监控页展示总功率、在线设备数、活跃告警数。
2. 用 ECharts 绘制最近 30 分钟功率曲线，处理空数据和缺失点。
3. 用图表展示各站点能耗，点击图表联动站点筛选。
4. 根据浏览器容器宽度调整布局，并在容器变化时调用图表 `resize()`。

**完成标准**：图表切换页面后不残留实例；窗口尺寸变化时不裁切；数据缺失时不把 `null` 错画成 0。

### 阶段 3：实时连接与一致性

1. 先建立实时连接并暂存事件，再请求带序号的快照；应用快照后处理序号更大的事件。若后端不能保证这段窗口，使用游标补拉。
2. 用 mock 服务每秒推送设备状态与测点；将消息放入小缓冲区并定时批量应用。
3. 按事件 ID 去重；发现序号缺口或断线后调用补拉接口。
4. 显示“已连接/重连中/数据可能过期”，重连使用退避策略。
5. 页面卸载时解除订阅；必要时由应用级服务统一持有连接。

**完成标准**：模拟断网 30 秒后能恢复；重复事件不会重复插入告警；旧事件不会覆盖新的设备状态；持续运行时内存和图表点数受控。

### 阶段 4：质量与交付

1. 用浏览器 Network/Performance 面板记录一次加载和一次实时更新的耗时。
2. 模拟 2000 台设备、1000 条告警，说明分页或虚拟滚动的选择。
3. 用真实机器检查普通笔记本、宽屏和高分辨率显示效果。
4. 编写 README：启动方式、角色账号、mock 切换、接口契约、架构图、取舍和已知限制。
5. 准备 3 分钟项目讲解、5 分钟技术深挖和一页问题复盘。

## 5. 必须模拟的异常场景

| 场景 | 预期处理 |
|---|---|
| API 很慢 | 保持明确加载状态，禁止重复提交；筛选变更时避免旧结果覆盖 |
| API 返回空列表 | 表达“暂无数据”或“筛选无结果”，保留清空筛选操作 |
| API 401 / 403 | 分别处理未登录/无权限；清理过期会话 |
| 设备测点 `null` | 显示“暂无数据”，不显示 0 kW |
| 推送重复或乱序 | 用事件 ID 去重、版本/序号判新旧 |
| 实时连接断开 | 显示数据可能过期并重连；恢复后补拉缺失事件 |
| 图表容器先隐藏后显示 | 显示后再测量/调用 `resize()`，避免空白或尺寸错误 |

## 6. 面试如何讲这个项目

### 3 分钟版本

1. **业务目标（20 秒）**：运维人员需要一个入口看设备状态、曲线和告警。
2. **个人职责（20 秒）**：我负责页面架构、实时数据处理、图表与权限。
3. **关键方案（90 秒）**：讲一个最有价值的技术难点，例如“快照 + 增量 + 补拉”如何保证断线恢复；画出数据流。
4. **结果（30 秒）**：给出练习项目中真实测得的数据或功能验收结果，明确这是练习项目。
5. **取舍和复盘（20 秒）**：哪些功能因时间没有做，若设备规模扩大下一步如何优化。

### 可能被追问

- 为什么选择 WebSocket 而不是 SSE？如果只需要服务器推送，SSE 是否更简单？
- 快照与消息之间如果有空窗，会不会丢事件？如何处理游标或序号？
- 图表点数持续增长时会发生什么？如何设窗口上限？
- 前端隐藏“确认告警”按钮后，接口还需做什么检查？
- 首屏变慢时，先量什么，再改什么？如何证明改动有效？

建议针对每个问题写下“我采用的方案、替代方案、为何这样选、实际验证方式”四句话。
