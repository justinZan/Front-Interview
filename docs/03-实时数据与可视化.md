# 03｜实时数据与可视化：WebSocket、SSE、ECharts 与监控大屏

> 适用场景：设备状态、实时曲线、告警推送、能量流图、站点拓扑和大屏。学习目标是能解释协议选择、写出可靠的连接逻辑，并能说明从消息到图表的完整数据链路。

## 一、先建立整体模型

一个实时看板通常包含以下链路：

```text
设备/网关 → 后端采集与计算 → 实时推送接口 → 前端连接层
                                             ↓
                                校验、去重、排序、补拉
                                             ↓
                                  业务状态 / 时间窗口
                                             ↓
                                   表格、图表、告警 UI
```

需要先向后端确认：消息 ID、设备 ID、事件类型、时间戳、序列号、单位、频率、断线后补偿方式。前端“收到消息”只代表传输成功，不代表状态一定完整或有序。

### 建议的消息契约

```ts
type DeviceStatus = 'online' | 'offline' | 'fault'

interface DeviceEvent {
  eventId: string          // 去重键
  sequence: number         // 同一数据流内递增；由服务端定义作用域
  deviceId: string
  occurredAt: string       // ISO 8601，明确时区
  type: 'status.changed' | 'metric.reported' | 'alarm.raised'
  payload: unknown         // 按 type 再细分并校验
}
```

不要仅按客户端收到的时间排序；网络延迟会改变到达顺序。页面展示时间时还要明确采用“设备发生时间”还是“平台接收时间”。

## 二、WebSocket 与 SSE

| 维度 | WebSocket | SSE（`EventSource`） |
|---|---|---|
| 方向 | 双向 | 服务端 → 浏览器 |
| 建连 | HTTP 升级为 WebSocket | 普通 HTTP 请求保持事件流 |
| 常见用途 | 设备控制、实时协作、双向消息 | 告警、状态和进度单向推送 |
| 浏览器重连 | 需要自己设计 | `EventSource` 通常自动重连；服务端可用 `retry` 字段提示间隔 |
| 消息恢复 | 协议不自动提供业务级恢复 | 可以用事件 `id` / `Last-Event-ID`，但历史保留和补发仍需服务端支持 |

**选择思路**：先看是否需要客户端通过同一连接向服务端发业务消息。只接收事件时 SSE 常较简单；双向控制或协议已有 WebSocket 网关时选 WebSocket。实际还要核对认证、代理超时、负载均衡、消息量和后端能力。

浏览器原生 `WebSocket` 构造器不能像 `fetch` 一样自定义任意请求头；原生 `EventSource` 也不提供任意请求头选项。认证方式要和后端、安全方案一起确定，避免把长期有效的 token 放在 URL 中。

### WebSocket 最小实现：连接、重连、清理

```ts
// useDeviceSocket.ts
import { onUnmounted, ref } from 'vue'

type ConnectionStatus = 'idle' | 'connecting' | 'open' | 'retrying' | 'closed'

export function useDeviceSocket(
  url: string,
  onEvent: (value: unknown) => void,
) {
  const status = ref<ConnectionStatus>('idle')
  let socket: WebSocket | null = null
  let retryTimer: ReturnType<typeof setTimeout> | null = null
  let retryCount = 0
  let stopped = false

  function connect() {
    if (stopped || socket) return
    status.value = 'connecting'
    const current = new WebSocket(url)
    socket = current

    current.onopen = () => {
      if (socket !== current) return
      retryCount = 0
      status.value = 'open'
      // 如协议要求，可在这里发送订阅消息。
    }

    current.onmessage = (message) => {
      if (socket !== current) return
      try {
        onEvent(JSON.parse(message.data as string))
      } catch {
        // 实际项目应记录脱敏后的解析错误，不让单条坏消息中断连接。
      }
    }

    current.onclose = () => {
      if (socket !== current) return
      socket = null
      if (stopped) return
      status.value = 'retrying'
      const base = Math.min(30_000, 1_000 * 2 ** Math.min(retryCount++, 5))
      const delay = base * (0.8 + Math.random() * 0.4) // 抖动，避免同时重连
      retryTimer = setTimeout(() => {
        retryTimer = null
        connect()
      }, delay)
    }

    current.onerror = () => {
      // 仅作诊断；通常由 close 事件统一安排重连，防止安排两次。
    }
  }

  function start() {
    if (!stopped) connect()
  }

  function stop() {
    stopped = true
    if (retryTimer) clearTimeout(retryTimer)
    retryTimer = null
    const current = socket
    socket = null
    current?.close()
    status.value = 'closed'
  }

  onUnmounted(stop)
  return { status, start, stop }
}
```

这个示例展示连接生命周期，生产实现还需要按协议补充：身份过期处理、订阅恢复、心跳/服务端超时、网络离线策略、快照补拉、消息格式校验。不要同时在 `error` 和 `close` 里安排重连，否则容易产生重复连接。

**思考题**：如果两个页面都调用该 composable，会发生什么？答案是通常创建两条连接。共享连接时可在业务服务层维护一个连接和多个订阅回调，订阅者数量为零时决定是否关闭；还要处理用户切换和登出。

### SSE 最小实现

```ts
const source = new EventSource('/api/devices/events')

source.addEventListener('device-status', (event) => {
  const data = JSON.parse((event as MessageEvent).data)
  // 校验 data，随后交给统一的数据处理函数。
})

source.onerror = () => {
  // 显示“连接中断/正在恢复”；不要每次 error 都新建一个 EventSource。
}

// 页面不再需要数据时：
source.close()
```

服务端事件流可能长这样：

```text
id: 1024
event: device-status
data: {"deviceId":"d-1","status":"online"}

```

空行表示一个事件结束。若希望断线续传，服务端需要保存可重放的事件，并识别事件 ID；浏览器自动重连本身不能保证没有数据丢失。

### 断线重连常见追问

1. **为什么指数退避还要加抖动？** 多客户端同时断开时，固定间隔会造成同步重连尖峰；抖动把请求分散。
2. **什么时候停止重试？** 用户主动退出、鉴权明确失败或业务不再订阅时停止；其他情况结合产品要求设置持续重试或上限和手动重试入口。
3. **网络恢复后如何保证图表正确？** 重新获取权威快照/缺失区间，再继续应用增量消息，不能只把曲线接着画。
4. **页面切后台要不要断开？** 根据消息成本、恢复能力和用户体验选择；至少要降低不必要的图表重绘，并保证回前台能补齐数据。

## 三、实时状态一致性

推荐服务端提供“**快照 + 增量事件 + 序列号**”契约。快照是某一序列位置的完整状态，增量事件表示之后的变更。

```text
1. 发起快照请求，同时暂存新到事件。
2. 收到快照（sequence = N），替换本地权威状态。
3. 丢弃 sequence <= N 的暂存事件。
4. 按序应用 N+1、N+2……；发现缺口则再次补拉。
5. 连接重建时重复上述过程。
```

这里的“按序”前提是服务端定义了**同一范围内连续递增**的序列号。若每台设备独立编号，就只能按设备维护序列，不可拿所有设备共用一个计数器。

```ts
interface DeviceDelta {
  sequence: number
  deviceId: string
  status: DeviceStatus
}

const lastSequenceByDevice = new Map<string, number>()
const statusByDevice = new Map<string, DeviceStatus>()

function applyDelta(event: DeviceDelta): 'applied' | 'duplicate' | 'gap' {
  const last = lastSequenceByDevice.get(event.deviceId)
  if (last !== undefined && event.sequence <= last) return 'duplicate'
  if (last !== undefined && event.sequence !== last + 1) return 'gap'

  statusByDevice.set(event.deviceId, event.status)
  lastSequenceByDevice.set(event.deviceId, event.sequence)
  return 'applied'
}
```

`gap` 出现后不要直接应用后面的状态并假装完整：应按接口能力请求缺失事件或重新拉该设备快照。告警还需要按告警 ID、版本和状态（新增、确认、恢复）处理，以免重复弹窗和“已恢复”再次显示为未处理。

### 高频数据降频显示

如果设备每秒发 100 个点，图表每条消息 `setOption` 一次，CPU 消耗可能主要来自前端渲染。可以将消息先写入队列，按固定显示频率（例如每 250 ms）批量取出；对趋势图保留最近时间窗口，并按可见宽度采样。状态卡片通常只需同一设备的最新值，历史点则另存或由服务端查询。

**需要权衡**：显示延迟、最大内存、历史精度、浏览器性能。不能为了“流畅”直接漏掉告警或影响业务要求的采样精度。

## 四、ECharts 生命周期与 Vue 3

图表容器必须有尺寸。创建实例后通过 `setOption` 设置或更新数据；容器变化后调用 `resize()`；容器被销毁前调用 `dispose()`。这些做法可在 [ECharts 容器指南](https://echarts.apache.org/handbook/en/concepts/chart-size/) 与 [动态数据指南](https://echarts.apache.org/handbook/en/how-to/data/dynamic-data/) 中核对。

```vue
<!-- TrendChart.vue：父组件传入新的 points 数组触发更新 -->
<script setup lang="ts">
import { onBeforeUnmount, onMounted, ref, watch } from 'vue'
import * as echarts from 'echarts'

type Point = [timestampMs: number, value: number]
const props = defineProps<{ points: Point[] }>()
const container = ref<HTMLDivElement | null>(null)
let chart: echarts.ECharts | undefined
let observer: ResizeObserver | undefined

function update() {
  chart?.setOption({
    xAxis: { type: 'time' },
    yAxis: { type: 'value' },
    series: [{ name: '功率', type: 'line', data: props.points, showSymbol: false }],
  })
}

onMounted(() => {
  const element = container.value
  if (!element) return

  observer = new ResizeObserver(() => {
    if (element.clientWidth === 0 || element.clientHeight === 0) return
    if (!chart) {
      chart = echarts.init(element)
      update()
    } else {
      chart.resize()
    }
  })
  observer.observe(element)
})

watch(() => props.points, update) // 使用不可变数组更新；原地修改不会触发此监听

onBeforeUnmount(() => {
  observer?.disconnect()
  chart?.dispose()
  chart = undefined
})
</script>

<template>
  <div ref="container" class="trend-chart" />
</template>

<style scoped>
.trend-chart { width: 100%; height: 320px; }
</style>
```

这是生命周期示例：项目中可按需引入 ECharts 模块减小包体积，并按产品要求补充 loading、空数据、错误和无权限状态。`ResizeObserver` 更适合监测容器尺寸；仅监听 `window.resize` 可能漏掉侧栏收缩、弹窗布局和容器显隐。

### `setOption` 的面试追问

- **动态数据如何更新？** 更新必要的 option 字段，保证序列 `name` / `id` 稳定；先用性能面板确认更新频率与耗时。
- **系列数量从多个变成一个，为什么可能留下旧系列？** 默认合并可能保留旧配置；检查 `replaceMerge` 或按需要重建 option 的策略。
- **何时选 Canvas 或 SVG？** ECharts 官方说明 Canvas 通常更适合大量图元，SVG 可能在大量小图实例/内存方面有优势；用目标设备、图表数量和真实数据量实测。[官方对比](https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/)
- **图表空白怎么排查？** 容器是否 0 宽高、实例是否绑定到已销毁节点、数据格式是否正确、页面显隐后是否 `resize`、控制台是否报错。

## 五、能源流图、站点拓扑与组态

这类页面先建模，再选择图形方案。建议把三类数据分开：

```ts
interface NodeModel {
  id: string
  kind: 'site' | 'device' | 'meter'
  label: string
  position: { x: number; y: number } // 画布或归一化坐标
}

interface EdgeModel {
  id: string
  sourceId: string
  targetId: string
  flowDirection?: 'forward' | 'reverse'
}

interface RuntimeModel {
  nodeId: string
  status: DeviceStatus
  powerKw?: number
  updatedAt: string
}
```

**职责分离**：拓扑结构描述节点与连线，布局数据描述位置，运行数据描述实时值。这样设备状态更新无需重建整张图。实际需求还可能涉及缩放/平移、点击详情、连线方向、异常高亮、图例、拖拽编辑、版本保存和跨屏适配。

选型时用一页原型验证节点数、交互和编辑需求。ECharts `graph` 可用于关系网络和展示型拓扑；复杂组态编辑可能需要更强的画布/流程图能力。面试时重点讲业务模型、交互约束和性能测量，而不是只报图形库名称。

## 六、大屏适配与可访问性

1. **先明确设计基准**：例如某固定宽高的大屏稿，以及实际投放设备的分辨率、缩放比例和浏览器。
2. **选择布局策略**：固定比例缩放适合受控的大屏播放场景；响应式网格适合多种宽高比。可以混合：外层栅格响应式，图内用相对坐标。
3. **图表随容器变化**：使用容器尺寸观察；隐藏 → 显示后确认尺寸并 `resize()`。
4. **关注可读性**：字体、单位、颜色对比、时间范围、空值含义和告警层级应适合远距离观看。颜色之外还应有文字或图形标识。
5. **明确异常状态**：网络断开、数据陈旧（如“最后更新于 14:32”）、权限不足、无设备和接口错误必须能区分。

## 七、面试问答速练

| 题目 | 合格答案应覆盖 |
|---|---|
| WebSocket 与 SSE 如何选？ | 通信方向、认证和部署约束、自动重连行为、服务端已有能力 |
| 如何避免断线后的数据缺口？ | 快照 + 增量、序列号、补拉/重放、乱序和重复处理 |
| 为什么图表越跑越卡？ | 高频重绘、无限增长的数据点、未销毁实例/监听、动画或标签开销；先测量再调整 |
| ECharts 为什么偶发空白？ | 容器 0 尺寸、显隐时机、实例绑定旧 DOM、数据或异常；有排查顺序 |
| 如何做站点拓扑？ | 节点/连线/实时值分层、布局与交互、库选型和性能边界 |
| 实时告警怎么去重？ | 告警 ID/版本、状态机、服务端权威状态、断线后补拉 |

答题时尽量补一句具体项目例子。例如：“我们把 1 秒内的多个功率点合并为一次图表更新，保留 30 分钟窗口；告警消息仍逐条处理，并用 ID 去重。”如果没有真实生产经验，明确说这是练习项目设计。

## 八、练习任务与验收标准

### 练习 1：实时设备列表

- 用 mock 服务每秒推送设备状态；列表可筛选在线/离线/告警。
- 断开网络 10 秒后恢复，页面显示连接状态，并通过快照恢复正确设备状态。
- 同一事件发送两次、事件乱序到达时，UI 不回退到旧状态。

### 练习 2：实时功率趋势图

- 展示最近 15 分钟功率；有单位、时间刻度、空状态和错误状态。
- 1000 个点持续更新时，点数和内存不会无限增长。
- 切换路由 20 次后，连接、定时器、`ResizeObserver` 和图表实例数量不会累积。

### 练习 3：站点拓扑与大屏

- 至少包含站点、电表和设备三类节点，连线方向可见。
- 状态变化只更新对应节点的样式/数值；点击节点打开详情。
- 在 16:9 与非 16:9 窗口下检查文字可读性、溢出和图表容器尺寸。
